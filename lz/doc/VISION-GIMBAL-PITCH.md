# 视觉调俯仰 —— 方案

> 状态：**方案（未实现）**。本文是设计文档，不是操作单；上机判据见
> [`ONDEVICE-CHECKLIST.md`](ONDEVICE-CHECKLIST.md)（待本文定稿后追加一节）。
> 建立时间 2026-09-25，此后代码若与本文冲突，**以代码为准并回来改本文**。

## 0. 一句话

**把「云台俯仰角」从「按几何公式算」改成「用相机看杆、把杆的中点对到画面中央」。**
几何公式仍然保留，但降级为**初始值**，不再是最终依据。

---

## 1. 为什么需要它

现在的俯仰角由 `LzPlan_ComputeGimbalPitchDeg()` 反算：

```c
俯仰 = -atan2(飞机相对目标高度 - 目标高/2, 半径)
```

这个公式是对的（2026-09-25 定案），但它**吃三个输入**，其中一个是猜的：

| 输入 | 来源 | 可靠吗 |
|---|---|---|
| 半径 | 操作员滑杆 | ✅ 明确 |
| 飞机相对目标高度 | 高度滑杆 + 起飞点/目标的椭球高 | ✅ 明确 |
| **目标高 `h`** | **`lz_pole_source.c:347` 与 `:389` 里写死的 `15.0`** | ❌ **猜的** |

`s_` 那两处的注释自己写着"国旗杆常见规格，绕飞不需要精确值"——
**那句话在公式写死 −15° 的时代是对的，现在不成立了**：公式现在直接用 `h`，
`h` 错多少，俯仰就错多少。

`h` 错 5 m（15 → 20）在默认剖面下（半径 12.5 m、高 80.9 m）差多少？

```
h=15: -atan2(80.9 - 7.5, 12.5) = -80.34°
h=20: -atan2(80.9 - 10.0, 12.5) = -80.05°   → 差 0.3°
```

0.3° 在 12.5 m 外是 **6.5 cm** 的偏移 —— 这个尺度下确实"不需要精确值"。
**但这不是重点。** 真正的问题是：

> **公式假设的一切（椭球高差、起飞点、目标高、云台真按指令转了）
> 只要有一处不对，相机就偏了，而画面上看不出异常。**

上一轮已经吃过一次同形状的亏：写死的 −15° 在默认剖面下差 65°，
飞机飞完了、航线是对的，**只是相机没对着杆**。`h` 只是同一类错误里
最显眼的那一个。

⇒ **把判断依据从"算式"换成"看得见的画面"**，这是本文的全部动机。

## 2. 核心认识：俯仰角就是「让杆中点居中的那个角」

几何公式与视觉瞄准**瞄的是同一个物理点**，不是两种不同的做法：

```
几何公式：-atan2(飞机相对目标高度 - h/2, 半径)   →  猜出「杆中点该在哪」
视觉瞄准：把检测到的杆中点对到画面中心 (0.5, 0.5) →  直接测出「它在哪」
```

`-h/2` 这一项就是"瞄杆的中点"（见 `lz_plan.h` 的 `LzPlan_ComputeGimbalPitchDeg`
注释：「与 `LzGeo_BearingDeg` 让机头瞄杆心同一个理由，水平方向瞄圆心、
垂直方向瞄半高」）。两边一致 ⇒ 两者可以互相校验，也可以互相替代。

**由此得出一条硬结论**（本文所有流程设计都建立在它上面）：

> 绕飞时**高度定、半径定 ⇒ 俯仰角恒定**（用户在 2026-09-25 指出）。
> 所以「测一次」与「持续测」在几何上**等价**，差别只在要不要对抗扰动
> （风把旗吹歪之类）。**本轮选「飞行前一次性测定」是充分的，不是妥协。**

## 3. 三个环节

```text
   ┌─────────────┐    ┌─────────────┐    ┌──────────────┐
   │ ① 取图      │ →  │ ② 量测      │ →  │ ③ 应用       │
   │ 拿到一帧 RGB│    │ 杆中点的 v  │    │ 写成 θ* 进 KMZ│
   └─────────────┘    └─────────────┘    └──────────────┘
    PSDK 取流           lz_vision           lz_plan / lz_wpml
```

### ① 取图 —— `lz/app/lz_vision_source.c`

`DjiLiveview_StartImageStream()` 直接给**解码后的像素帧**，
头文件 `@note This interface support on DJI manifold3` —— 正是我们的机型。

```c
T_DjiReturnCode DjiLiveview_StartImageStream(
    E_DjiLiveViewCameraPosition position,   /* DJI_LIVEVIEW_CAMERA_POSITION_NO_1  (1) */
    E_DjiLiveViewCameraSource   source,     /* ? 见下方待定项 */
    E_DjiLiveViewPixFormate     pixFmt,     /* PIXFMT_RGB_PACKED (5) */
    DjiLiveview_ImageCallback   callback);
```

回调签名（`dji_liveview.h:201`）：

```c
typedef void (*DjiLiveview_ImageCallback)(E_DjiLiveViewCameraPosition position,
                                          const uint8_t *buf, uint32_t len,
                                          T_DjiLiveviewImageInfo ImageInfo);
/* T_DjiLiveviewImageInfo = { E_DjiLiveViewPixFormate pixFmt; uint16_t width, height; uint32_t frameId; } */
```

⚠️ **`buf` 在回调返回后即失效** —— 这是从官方样例反推的，**不是文档写的**：
`dji_liveview_object_detection.cpp:557` 一进回调就 `cv::Mat(...).clone()`，
`test_liveview.c` 里则是立刻 `fwrite`。两种做法都指向"不能存指针"。

⇒ 本模块的做法是**在回调里拷进内部缓冲**（见 §7 的骨架）。回调跑在 SDK
线程上，与「控件回调不能阻塞」是同一条纪律。

### ② 量测 —— `lz_vision.c` 已有的东西 + 一处缺口

现有 `LzVision_Detect()` 可靠给出的是：

| 字段 | 含义 | 可信度 |
|---|---|---|
| `pixel.u` | **杆列**的归一化横坐标 | `[V]` 实测 0–2 px 稳定，6 张照片回归守着 |
| `pixel.topV` / `bottomV` | **旗面**框的上下边 | `[V]` 同上 |

⚠️ **但"杆的中点"要的不是这两个 —— 这是本方案唯一的算法缺口。**

"整根杆的中点"需要杆自身的上下端。现在 `lz_pole_extent()` 算了这个值，
**却在 `lz_vision.c:610-611` 被 `(void)` 丢掉了**：

```c
int poleTop = -1, poleBottom = -1;
lz_pole_extent(vision, frame, poleX, &poleTop, &poleBottom);
(void)poleTop;      /* ← 算出来没用 */
(void)poleBottom;
```

而且它**从未被验证过**（6 张照片的黄金值里只有杆列 x，没有杆的上下端）。
`lz_pole_extent` 的判据是"对比度命中的连续段"，杆压在不同背景上时可能断续 ——
它是为"折算置信度"写的，不是为"测端点"写的。

**两条路，实施时按成本从低到高试**：

| | 杆中点怎么定 | 前提 | 风险 |
|---|---|---|---|
| **A** | `(旗面顶 + 杆底) / 2`，杆底取 `lz_pole_extent` 的 bottom | 只需把丢弃的值接上 | 杆底可能断续、可能停在旗下方某处 |
| **B** | `旗面框的中点` | 零改动 | **旗在杆顶**（现场形态 `[V]`）⇒ 旗中点 = 杆顶部，**不是杆中点**。瞄准点偏上 ⇒ 俯仰偏浅 |

⚠️ **A 和 B 不是"误差大小"的差别，是"瞄错点"的差别。** 现场是
"旗在杆顶、迎风向水平展开"（2026-09-25 核实）—— 一根 15 m 的杆，
旗面占顶上 1.5 m，旗中点比杆中点**高 6.75 m**。在 12.5 m 外那是 28°。
所以 **B 只能当"检测不到杆端点时"的降级方案，且必须报出来**
（"⚠ 只认到旗面，俯仰按旗心算"），不能静默降级。

**杆底还有第三条路，现场成本最低**：激光。`LzPole_RecordLaser()` 已经能拿到
瞄准点的**椭球高**（`info.altitude`，单位 0.1 m）。若激光正打在杆上，
杆底椭球高就有了 —— 比在画面里找杆底可靠得多。列为备选，见 §9。

### ③ 应用 —— 写进 KMZ

测出 `θ*` 后，走**既有链路**，只换一个数：

```c
LzOrbitProfile profile = { ... };
profile.gimbalPitchDeg = thetaStar;   /* ← 原来由 autoGimbalPitch 反算 */
profile.autoGimbalPitch = false;      /* ← 关掉反算 */
```

`LzPlan_BuildOrbit()` → `LzWpml_Build()` 已经把 `gimbalPitchDeg` 逐点写进
`<wpml:gimbalPitchRotateAngle>`，`LzPlan_Validate()` 也会照旧用
`[-90, 30]` 拒越界值。**③ 这一环不需要新代码**，只需要一个能写进去的入口。

## 4. 为什么"飞行前一次性测定"是对的选择

除了 §2 那条几何理由，它还**顺带避开了一个真实冲突**：

> 用 `DjiGimbalManager_Rotate()` 在任务执行中调云台，会与航线里的
> `<wpml:gimbalRotate>` 动作**抢同一个云台**。两者谁赢没有文档说明，
> 也没有实测过。

飞行前测定 ⇒ 测完就把值写进 KMZ ⇒ 任务期间**只有航线在动云台**，
不抢。等将来真要"飞行中持续微调"时再处理这个冲突。

⚠️ **但要留一句话**：`towardPOI` 让机头追杆（yaw），而
`gimbalYawRotateAngle` 必须与 `aircraftHeading` 一致（规范三处都标）。
**那是 yaw，与本方案管的 pitch 不冲突** —— `gimbalPitchRotateEnable`
与 `gimbalYawRotateEnable` 是独立的两行。所以本方案不改变
CLAUDE.md「绕飞怎么让相机盯着杆」那一节的结论。

## 5. 需要新增的流程步骤

现在的流程：

```text
拨 ON → 取圆心 → 规划 → 生成 KMZ → 上传 → 启动
```

测定插在哪，有两个方案。**推荐 A**（不碰飞控 API）。

### 方案 A：操作员手动飞到观测位，按按钮测定（推荐）

```text
操作员：起飞 → 手动飞到「水平距离 = 半径、相对高度 = 高度」处 → 按「视觉标定俯仰」
程序：  ① 设云台俯仰 = 几何反算初值  ② 等画面稳定  ③ 检测 → 算 θ*
        ④ 浮窗报告「杆中点原在 v=0.62，已把俯仰从 -80.3° 改为 -81.9°」
操作员：拨 ON → （用 θ* 生成 KMZ）→ 上传 → 启动
```

**新增控件 6**：`button` / 「视觉标定俯仰」。

为什么推荐它：

- **完全不碰飞控 API**。不需要 `DjiFlightController_*`（那是高级功能，
  M4T 上要妙算3 才开放，且要申请权限的可能）。
- **人始终在环** —— 与项目一贯的安全取向一致（拨 OFF 是急停、
  飞完不自动返航、fail-closed 划在「作业开始」）。
- **观测位不必是首航点**。圆是各向同性的，只要"水平距离 = 半径、
  相对高度 = 高度"就成立，**方位角随便**。操作员好飞。

⚠️ 操作员必须**手输**当前的高度/半径，或者程序读滑杆值提醒他
（浮窗："请飞到 距离 12.5 m、相对高度 80.9 m 处"）。**若实际飞到的位置
与滑杆不符，测出的 θ* 就是错的** —— 所以浮窗上要同时回显这两个数，
让操作员自己核对。这是方案 A 的主要代价。

### 方案 B：程序自己飞到首航点，自动测定

```text
拨 ON → 取圆心 → 规划 → 用 DjiFlightController_SetModeStartMission 飞到首航点
      → 悬停 → 测定 → 用 θ* 重新生成 KMZ → 上传 → 启动（飞机已在首航点）
```

自动、不需要操作员配合，观测位严格等于首航点。代价：

- 需要飞控接口（`DjiFlightController_ObtainJoystickCtrlAuthority` +
  `ExecuteJoystickAction`，或 `SetModeStartMission`）。
  ⚠️ API-MAP §12.4 记：`T_DjiFlightControllerStartMissionReq` 的
  `goal_num` 注释写明 "currently only supports one point" —— 只能单点。
- **fail-closed 边界要往前挪**：程序开始自己控制飞行了。
- 上机调试面变大（飞控 + 取图 + 视觉三者同时不确定）。

⇒ **本轮按方案 A 实施**，B 留作将来"全自动"的选项。

### 6.3 垂直 FOV 怎么算（把 82° 用对）

设画面宽 `W`、高 `H`、对角 `D = √(W²+H²)`。小孔成像下三条视场角满足：

```
tan(HFOV/2) = (W/2)/f
tan(VFOV/2) = (H/2)/f
tan(DFOV/2) = (D/2)/f
⇒ tan(VFOV/2) = tan(DFOV/2) · H/D
```

规格是 4:3（8064×6048）时 `H/D = 3/5`：

```
tan(VFOV/2) = tan(41°) × 0.6 = 0.8693 × 0.6 = 0.5216
VFOV ≈ 55.1°
```

**对照错误算法**（把 82° 当水平 FOV，4:3）：

```
tan(VFOV/2) = tan(41°) × 3/4 = 0.6520  ⇒  VFOV ≈ 66.2°      ← 差 11°
```

两者都"看着合理"，只有量纲分析能分辨。⇒ **实现时把这个算式写成
一个纯函数并加测试**（`LzVision_VerticalFovDeg(frameW, frameH, diagFovDeg)`），
放 `lz_core` 或 `lz_vision`，**桌面上就能测**。

## 7. 分步实施

每步都有**桌面可测的部分**，先做能测的。

### 步骤 1 —— 取图接线骨架（本次已做）

`lz/app/lz_vision_source.{h,c}`：`StartImageStream` + 回调拷贝进内部缓冲 +
`Peek` / `CopyLatest`。**不含**检测，不含云台。

配套探针 `lz/app/lz_liveview_probe.c`（与 `lz_rangefinder_probe` 同一模式）：
上机打印相机类型、可用的 stream source、每帧的尺寸/格式/帧号，
并**存一帧为 PPM** 供本机核对。

**为什么必须有探针**：骨架本身在主链路里没有调用点（测定还没做），
不写探针就**无法验证接线对不对** —— 而"没变红的反向验证等于没测"
是本项目已写进 CLAUDE.md 的教训。

### 步骤 2 —— 垂直 FOV 纯函数 + 测试

`LzVision_VerticalFovDeg(w, h, diagFovDeg)`，放 `lz_vision`（零依赖）。
测试断言：4:3 + 82° → 55.1°±0.1；16:9 + 82° → 另一值；
**反向验证**：把它写成"水平 FOV 当输入"的错误版本，测试必须变红。

### 步骤 3 —— 杆端点

把 `lz_vision.c` 丢弃的 `poleTop/poleBottom` 接上，填进 `LzPixelBox`。
需要新增字段（`poleTopV` / `poleBottomV`）—— 那是 **`LzTarget` 契约的改动**
（`lz_target.h` 是视觉与规划之间唯一契约，改动要同时改两侧）。
6 张照片的黄金值要补上杆的上下端（**人工目视核对后再平移**，
不能取算法自己的输出，否则是循环论证）。

### 步骤 4 —— 像素偏差 → 角度

```c
/* v 是画面中心的偏差；VFOV 由步骤 2 给 */
double deltaDeg = atan((vMid - 0.5) * 2.0 * tan(vfovDeg * M_PI / 360.0)) * 180.0 / M_PI;
double thetaStar = theta0 - deltaDeg;    /* theta0 = 测时云台的实际俯仰（读回） */
```

⚠️ 用 `atan` 而不是线性 `(vMid-0.5)*VFOV`：VFOV=55° 时线性近似在边缘差
约 3°。**这个函数是纯数学，桌面可测**，测试要覆盖 vMid=0.5 → 0、
vMid=1.0 → 半个 VFOV、以及符号（vMid>0.5 ⇒ θ 更负 = 下压）。

### 步骤 5 —— 云台设置 + 读回

订阅 `GIMBAL_ANGLES`（走回调缓存）+ `DjiGimbalManager_Init/SetMode/Rotate`。
先**只做"设一个角、读回来核对"**这一件事，做成探针的一步 ——
在 #555/#563 的阴影下，"能不能控制自带云台"本身就是要验的。

### 步骤 6 —— 接进流程（方案 A）

控件 6 + 状态机里一条"测定"分支。测定结果存进 `LzPole` 旁边
（或一个 `LzGimbalCalib` 小结构），`lz_mission.c` 生成剖面时用它。

## 8. 桌面可测 vs 只能上机

**这一节决定了实施顺序** —— 能在桌面测的先做。

| 可以桌面测（`ctest`） | 只能上机 |
|---|---|
| 垂直 FOV 换算（步骤 2） | 取到的是哪个镜头的画面（§9 #1） |
| 像素→角度换算（步骤 4） | 帧的真实分辨率/格式/通道顺序 |
| 杆端点检测 + 黄金值（步骤 3） | 图像流的帧率与稳定性 |
| 剖面里 `gimbalPitchDeg` 的写入与校验（③，已有测试覆盖） | 云台能不能被程序控制（#555/#563） |
| 测定失败时的回退路径 | 读回云台角是否可信 |

**骨架（步骤 1）落在这两栏之间**：`lz_app` 能在 x86_64 上编出来并链接
（Payload-SDK 自带 x86_64 静态库 `[V]`），**但不等于跑得起来** ——
设备没有 `/dev/usb-ffs/bulk*` 时会在 `hal_usb_bulk.c` 报
Bad file descriptor，这是预期的。所以步骤 1 的验收只有"编译链接通过"。

## 9. 待定项（每项带判据与回退）

按**必须先答**排序。

### #1 取到的是哪个镜头的画面？**（头号，卡着 §6.3 的换算）**

`E_DjiLiveViewCameraSource` 里 M4T 有 `M4T_VIS=1` / `M4T_IR=2` / `M4T_4K=3`，
但 M4T 的镜头是**广角 82° / 中长焦 35° / 长焦 15°** —— **对不上**。
`VIS` 是哪一个？不知道。

- **判据**：探针存下的那帧 PPM，在本机看画面内容与视场。
  对准一个已知尺寸的目标（比如杆），由"目标占画面比例 + 已知距离"
  反推 FOV，看落在 82°/35°/15° 哪个上。
- **顺便答的**：通道顺序（红旗是红的还是蓝的 ⇒ RGB 还是 BGR）、
  真实分辨率、宽高比。
- **回退**：若在运行期取不到可靠的 FOV，改为**一次性标定**并把值写进配置；
  或改用"两次测量消去 FOV"的办法（挪一段已知距离，看 v 的变化量）——
  后者不需要 FOV，代价是多一次操作。

### #2 激光打的是不是图像流里那个镜头？

若图像流给的是长焦而激光同轴在广角上，则"视觉检测杆"与"激光打杆"
指向不同的画面中心 —— 那么步骤 4 的 `vMid` 与 `theta0` 的关系就断了。

- **判据**：激光照射时看 `T_DjiCameraManagerLaserRangingInfo.screenX/screenY`
  （单位 **0.1%**，即屏幕归一化坐标 ×1000）—— 它给的就是**激光点在画面中的位置**。
  与图像流里检测到的杆列 `pixel.u` 对照，一致就说明同轴。
  ⚠️ **这是一个可以直接算出来的判据，不需要猜** —— 优先级很高。
- **回退**：若不同轴，改用激光点位置作为瞄准基准（激光点也在画面里，
  同样能算偏差）。

### #3 隔离等级：能不能用现成的无人机视角换算？
（若 #1 回退到"标定"，本节无需）

### #4 `h` 还要不要？

若视觉测定走通，`h`（`lz_pole_source.c` 里写死的 `15.0`）就**只用于算初值**。
初值不准无所谓 —— 测定会修正它。

但有一条路值得留着：**用视觉/激光测出 h 本身**（§3 的备选）。
那样俯仰初值就是准的，测定变成"校验"而不是"必需"。
⇒ 记为将来的改进，**不在本轮**。

### #5 帧率、延迟、稳定性

画面从相机到回调有多少延迟？30 fps 稳不稳？丢帧多不多？
- **判据**：探针跑 60 s 统计帧数与间隔分布。测定流程里"等画面稳定"
  需要知道要等多久（几帧）。
- **回退**：若丢帧严重，多取几帧做中位数（杆列已经证明是稳定量，
  取中位数代价很低）。

### #6 `DjiHighSpeedDataChannel_SetBandwidthProportion` 要不要调

官方样例调了（10/60/30），但头文件说需先注册 network handler，
而我们的平台层没注册。默认 33/33/34。
- **判据**：不调，看图像流是否正常。正常就不动 —— **少一个自由度**。

### #7 编码回调（`RegEncoderCallback` / `EncodeAFrameToH264`）要不要注册

不注册的后果是**无法把识别框推给 Pilot 显示**（`SendAiMetaToPilot`）。
本轮不需要显示，所以不注册。
- ⚠️ 但要注意：不注册编码回调时，取图这条路是否仍然正常？**未确认。**
  官方样例两条路都注册了。探针里先只注册取图，看能不能收到帧。
