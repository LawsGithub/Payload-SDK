# 判据抽进 lz_core · 测试框架 · 反向验证 · 本机自检三武器

> 从 `CLAUDE.md` 外置（2026-10-10）。这一整块是本项目的方法论核心：
> 为什么判据必须抽到零依赖层、测试框架自身的计数为什么必须对称、
> 每修一处必须逐条回退确认变红、以及 ASan/aarch64/覆盖率三样武器。
> 信任标记：`[V]` 已用命令验证 · `[?]` 仅记忆未复核 · `[X]` 已证伪。

## 失败可观测性：三条"看起来有、实际没有"的坑 `[V]`（2026-09-21 审计）

这三条都是"代码写了、注释说得像真的、但实际没生效"，比明显的 bug 危险：

### 1. PSDK **没有**反向推控件状态的接口 —— 别写"把开关拨回去"

`lz_widget.c` 曾这样写，注释还写着"程序化拨回 OFF"：

```c
(void)LzWidget_SetWidgetValue(DJI_WIDGET_TYPE_SWITCH, ..., OFF, NULL);  // 空头承诺
```

那是**我们自己**注册给 SDK 的回调，被 Pilot 调用时才生效；直接调它只改本地变量。
`dji_widget.h` 全部 **9 个**导出函数里没有任何 setter；`dji_widget_manager.h` 的
`DjiWidgetManager_SetWidgetState` 目标是**机上挂载的负载**，不是本应用在 Pilot 的 UI。

**真实后果**：开关**保持 ON**（持续可见）而浮窗说"绕飞结束"（会被下一条覆盖）——
矛盾的两条信息里，持续可见的那条是错的。现在的做法是如实提示
"⚠ 开关仍在 ON 位，请手动拨回"。

### 2. 浮窗去重表：发送失败也标记"已发" = 该消息永不重发

`LzWidget_MsgTask` 里发完就 `memcpy(lastMsg, ...)`，一次失败（通道未就绪）
就让这条消息**永远消失**。浮窗是室外**唯一**的反馈通道，
"启动被拒：…" 丢了等于没有反馈。**只在返回成功时才更新去重表。**

### 3. `(void)f()` 丢掉的是"停止失败"

拨 OFF 的 `(void)LzBridge_StopMissionV3()` 曾把 STOP 失败完全吞掉，
随后照样报"绕飞结束"。**静默的失败等于假装成功**，而在飞控语境里
这直接关系到安全（飞机还在杆旁边绕，操作员以为停了）。
现在：加日志、检查返回值、失败时**保持 RUNNING**（状态与事实一致）
并只报一次浮窗（Tick 是 100 ms 一拍，不加闸会每秒刷 10 条）。

## 测试框架：0 项检查也算失败 `[V]`（2026-09-21）

`LZ_TEST_SUMMARY()` 现在把"检查项数为 0"判为失败。

**为什么**：本工程的用例大量写成 `if (obj != NULL) { LZ_CHECK(...) }`。
一旦构建静默失败（缓冲区算小了、入参校验误拒），那些断言**整体不执行**，
汇总打印"0 项检查，0 项失败"并返回 0 —— **测试绿着，但什么都没验**。
这种"空跑成功"比失败更危险：它让一次真实的回归伪装成通过。

## 反向验证：修复必须能变红 `[V]`（2026-09-21 起执行）

每修一处关键缺陷，都**逐条回退该修复、确认对应断言变红**，再恢复。
2026-09-21 那轮实测：

| 回退的修复 | 变红的断言 |
|---|---|
| wpml 三元素（`globalRTHHeight`/`yaw` 归一/…） | 12 条 FAIL |
| 安全包线检查 | 6 条 FAIL |
| 零检查守卫 | 单跑空测试退出码 1 |

**不这么做的代价**：断言可能因为某个前置条件恒假而从未真正执行过 ——
那正是本项目已经踩过的形状（`LZ_TODO_PENDING`、`if (f.xxx != NULL)` 守卫）。

**2026-09-23 那轮实测**（本次交接用新鲜构建重跑，从全新 shell 取真实退出码）：

| 状态 | `lz_test_plan` 退出码 | ctest |
|---|---|---|
| 基线与远端一致 | 0（1075 项检查，0 失败） | 100% passed, 0 failed out of 7 |
| 只拆闭合（`i <=` 改回 `i <`） | **1**（1040 项检查，172 项失败） | 71% passed, **2 failed** |
| 只让 `LZ_CHECK_ANGLE_NEAR` 不计数 | 0（1075 项检查，0 失败） | 100% passed —— **看起来全绿** |
| 宏带 bug + 9 条纯角度断言失败 | **0、且汇总打印"0 项失败"** | **100% passed** ← 真实失败被伪装成通过 |
| 上一条把宏修好 | **1**（1075 项检查，9 项失败） | 86% passed, 1 failed |

第 4 行是这次实测**唯一能演示该 bug 的构造**：拆闭合那条路径的断言全走
`LZ_CHECK`/`LZ_CHECK_NEAR`，用不上角度宏，所以宏坏掉时它的 172 条失败里
仍有 143 条被正常计数、ctest 照样变红 —— **掩盖不了**。
必须**单独**让一条只用角度宏的用例失败（这里把 `toPole` 人为偏 45°），
才能看到"`0 项失败` + ctest 全绿"这个假象。
⇒ **反向验证要按宏逐条做，不能用一条路径一次测完所有修复。**

## 本机自检的三条新武器（2026-10-06/07）`[V]`

设备不在线的那几天加的三样，都不需要设备，**加起来 2.5 秒**：

### 1. ASan + UBSan（`-DLZ_SANITIZE=ON`，precheck 3b）

第一次跑就抓到一处 **use-after-free**：`lz_detect_pole_column()` 里
`free(votesHist)` 写在中位数那段**之前**，而那段紧接着就读它。
被释放的 1252 字节通常还没被复用 ⇒ 读到原值 ⇒ **测试全绿、黄金值全对**；
换个分配器/负载/优化等级就会变成错值或崩溃。

⚠️ **判据**：本项目的判据大量是"数值算错但**不崩**"的形状，而内存类缺陷
恰恰也是"不崩只错" —— 两者叠在一起，普通构建根本看不出来。
**只有消毒器抓得到。**

### 2. 本机 aarch64 交叉编译（precheck 3c）

**先说清楚它不能证明什么**：产物要求 GLIBC_2.34、设备 2.31 ⇒
**产物在设备上跑不起来**，硬约束「绝不在本机交叉编译交付产物」**不变**。
（那 2.34 来自 `libpayloadsdk.a` 里的 `dlopen`/`dlsym`，不是我们的代码。）

它的用处：**把"设备上才会撞到的编译错误"提前**。整个 PSDK 应用编一遍
**2 秒**。反向验证：塞一个 `unsigned int a : 40` 位域 ⇒ 桌面构建不报、
3c 报 `error: width of 'a' exceeds its type`。

⚠️ 它现在带 `-DLZ_POLE_SOURCE_LASER=ON` —— 专门让"`#ifdef` 里编不过"
那类问题暴露（`lz_test_pole.c` 里曾有一段**从未被编译过**的代码）。

### 3. 覆盖率基线（precheck 3d，门槛 80%）

**刻意不当 KPI** —— 覆盖率是"判据抽到桌面可测位置"的副产品，
拿它当目标会诱导写"走过场"的用例。它的用处是**发现"判据被搬回 app 层"**：
抽走时会跳、搬回去时会掉。实测最低 87.10%。

⚠️ **3d 自己踩了两个坑**（都修了）：
1. **gcov 的汇总行打在 stdout，不在 `.gcov` 文件里** —— 第一版 grep 文件，
   于是**永远取到空值、检查恒绿**。又一个"看起来在跑、实际什么都没查"。
2. **`lz_test_vision` 必须也算进来** —— 漏了它 `target.c` 只有 19%
   （实测），会被误读成"判据被搬回 app 层了"。
   ⇒ **统计口径要先对齐**：`.gcda` 是按"哪个测试走到了它"累加的。

### 全项目覆盖率基线（gcov，全部测试目标合并）

| 文件 | 覆盖 | 文件 | 覆盖 |
|---|---|---|---|
| `types.c` | **100.00%** | `align.c` | 98.67% |
| `mission_logic.c` | **100.00%** | `wpml.c` | 96.37% |
| `bridge.c` | 93.33% | `gimbal_status.c` | 95.12% |
| `geo.c` | 91.80% | `vision_shared.c` | 91.25% |
| `kmz.c` | 90.48% | `plan.c` | 88.98% |
| `vision.c` | 88.40% | `target.c` | 87.10% |

### 顺手补掉的三处真缺口（都是覆盖率查出来的）

1. **`types.c` 46% → 100%**：`LzStatus_Str()` 整张文案表零覆盖 ——
   漏一项会落到 `default` 返回"未知状态"，而**调用方照样能编译能跑**，
   只是操作员看到一句没有信息量的话。
2. **`kmz.c` 的两处守卫**：拆掉 `LzKmz_Crc32(NULL, n>0)` 与
   `count > 0xFFFF` 两条守卫，实测都是 **rc=139（SIGSEGV）**，
   不是干净的 FAIL。⇒ **"守卫没有测试"= 没人知道它还在不在**，
   而崩溃会发生在调用方身上。
3. **`vision.c` 的 `LastMiss` / `EstimateSize`**：前者主应用在用
   （区分"没红块"与"置信度不足"，混了会把操作员引偏），
   后者**没有调用方** —— 而"没有调用方 ⇒ 判据没人验 ⇒ 更要补测试"。

## 绕飞状态机的**转移表**抽进 `lz_core` `[V]`（2026-10-07）

**一句话**：整张状态转移表此前在 `app/lz_mission.c` 里 ⇒ 桌面测不到 ⇒
**一条断言都没有**。而走错的后果是**安全相关的谎话** ——
"飞机还在杆旁边绕，而日志与界面都说已经停了"。

`LzMission_Tick()` 里只有 **2 个** SDK 调用（启动航线 / 停止航线），
其余全是判据 ⇒ 决策可以整个搬走。

### 两相式：SDK 调用夹在中间，所以必须两步

```text
LzMission_Decide(输入)      → 决策{该做什么 + 去重闸的新值}
（调用方调 SDK，拿到结果）
LzMission_Apply(决策, 结果) → {新状态 + 要不要报哪条消息}
```

两步都是**纯函数**：不读全局、不调 SDK、不打日志。
`lz_mission.c` 只剩"读输入 → Decide → 调 SDK → Apply → 呈现"。

⚠️ **`Apply` 的输出状态是权威的** —— `step == NONE` 时它原样带回传入的
当前状态。第一版没把 `state` 放进输入、靠"调用方在 `step == NONE` 时
**别采纳** `o.state`"来兜 —— 那种"记得别用"的约定一定会有人忘，
而忘了的表现是 **RUNNING 被悄悄打回 IDLE**（开关还在 ON ⇒ 下一拍重新上传启动）。

### 三条"刻意如此"（都有断言守着）

1. **照准在跑时不启动绕飞，但也不清开关** —— 操作员的意思多半是
   "先识别、再绕飞"，清掉开关会逼他再拨一次 ON（而他记得自己拨过了）。
   `B2` 断言的是 `step == NONE`（"什么都别做"），不是"清了开关"。
2. **停止失败时留在 RUNNING** —— 状态必须与事实一致。若置 IDLE，
   开关还在 ON 位而状态机认为空闲，下一拍会把它当成**新的绕飞请求**
   重新上传启动。`D2` + `D3` 是一对，缺一不可。
3. **三个去重闸各自独立** —— 合并会让某条消息被另一条吃掉（`F4` 守着）。

### ⚠️ 两处"想当然"都踩了

**① 第一版把"飞机侧报结束"写成 `step = NONE`**，理由是"没有判据，
只有读原因 + 改状态"。**那是错的** —— "RUNNING + ended ⇒ 收尾"本身就是
判据，写成 NONE 等于把它留在 app 层测不到。⇒ 加了专门的
`LZ_MISSION_STEP_MISSION_ENDED`。

**② precheck 的第一版检查数全文有几处 `s_state = IDLE`** —— 而
`Init` / `DeInit` 里本来就有两处合法的 ⇒ **恒红**。改成**抠
`LzMission_Tick()` 的函数体**再查。与「`teardown()` 要抠函数体」是
同一个教训：**数全文出现次数不够，要问"在哪个函数里"。**

### 测试：逐条 + **穷举**

`lz_test_mission`（54 项断言）分七组，另加一条**穷举**：

```text
2(状态) × 2(开关) × 2(照准) × 2(结束) × 2(去重闸) = 32 组输入
四条不变式：
  1. step == NONE  ⇒ 状态**原样保持**
  2. 最多报**一条**消息（浮窗带宽 2 KB/s）
  3. IDLE 且开关 OFF ⇒ 什么都不做
  4. 照准在跑 ⇒ **绝不**启动绕飞
```

穷举的价值：逐条用例只能覆盖想到的组合。实测把不变式 1 的修法拆掉，
`E3` 与 `G1` **同时**变红。

覆盖率：`lz_mission_logic.c` **100% of 74 行**。

### 反向验证（逐条回退，全部实测变红）

| 回退的改动 | 变红 |
|---|---|
| 停止失败时置 IDLE 而非 RUNNING | **2 项**（D2、D3） |
| 停止失败也报 `reportOperatorStop` | 1 项（D2） |
| 照准那条去掉去重闸（每拍都报） | 2 项（B3） |
| 操作员拨回 OFF 时不归零去重闸 | 1 项（B5） |
| `Apply` 在 `step == NONE` 时返回 IDLE | **2 项**（E3、G1） |
| `ShouldNoteEnded` 不看状态直接 true | 1 项（E1） |
| `ShouldReportWaypoint` 去掉"变了才报" | 1 项（F1） |
| `Decide` 在 RUNNING+ended 时给 NONE | **3 项**（E2 组） |

## 「原始读数 → 该记什么」抽进 `#ifdef` 之外 `[V]`（2026-10-06）

**一句话**：激光记录那条路上，**单位换算 + 三道闸 + 目标高分类**此前全在
`#ifdef LZ_POLE_SOURCE_LASER` 里面 —— 桌面构建不编它，于是**一行都测不到**。

**判据（实测确认，不是推测）**：把 `info.distance / 10.0` 改成 `/ 100.0`，
**没有任何测试变红**。而表现是"距离小十倍"，看起来仍像个合理的读数。

⇒ 抽成零依赖的 `LzPole_PrepareLaserRecord()`（在 `#ifdef` 之外），
`LzPole_RecordLaser()` 只剩**取数**与**按分类打日志**。

### 顺带抽出的两个**分类**枚举（都因为"处置不同"）

```c
LzLaserMiss          NO_DISTANCE / BAD_COORD / NULL_SOLUTION / NONE
LzLaserHeightDiag    NA / NORMAL / GROUND / OVER_MAX / NO_HOME
```

**为什么必须分得开**：三种 miss 的处置完全不同 ——
无距离 ⇒ **重新瞄准**；坐标越界 ⇒ 报 bug；零解 ⇒ **等定位，别调瞄准**。
合并成一个 `LZ_ERR_NO_TARGET`、只靠日志文案区分的话，"分得开"这件事
**本身就没有断言守着**，文案改一个字就静默退化了。
与 `LzVisionMiss` 是同一个形状（那边踩过：主应用只报了"检查取景"，
把操作员引去反复调瞄准，而病因在代码里）。

`LzLaserHeightDiag` 同理：**"打地面"是合法用法**（点目标，瞄它自身），
而"超上限"要操作员核对参考面 —— 两者**都返回 0**，
只断言返回值的话两条用例一模一样，等于没测。**断言的是分类。**

### ⚠️ 两个枚举的 0 值都踩过一次

1. **`heightDiag` 的 0 曾是 `NORMAL`** —— 而早退路径（`miss != NONE`）
   `memset` 之后它就是 0，读起来像**"目标高算过了，正常"**。根本没算。
   ⇒ 改成 `LZ_LASER_TH_NA = 0`，早退时显式置它。
2. **`LZ_LASER_TH_NO_LASER_ALT` 是个到不了的分支** —— 实测
   `altitudeDm = NaN` 时 `LzGeo_IsValid()` 的**有限性检查**在更前面
   就把它拦成 `BAD_COORD`，函数早退。**加一个到不了的分支 = 加一段
   没人能验的代码**，已删。这条是"想当然地补一个防御分支"的典型代价。

### ⚠️ 测试文件里一段**从未被编译过**的代码 `[V]`

`lz_test_pole.c` 里曾有一段 `#ifdef LZ_POLE_SOURCE_LASER` 包着的
`LzPole_RecordLaser(&pos)` —— 而那个函数的签名是 `(void)`，传参会编译失败。
之所以一直没暴露：**桌面构建从不定义那个宏**，整块被预处理掉了。

⇒ **`#ifdef` 里的代码不只是"可能没跑"，是"可能连编译都没过"。**
要验它，得**显式带那个宏编一遍**（`precheck.sh` 3c 现在带
`-DLZ_POLE_SOURCE_LASER=ON` 交叉编译整个应用，就是为这个）。

### 覆盖率的实测变化

`lz_pole_source.c` 用 gcov 测（`--coverage`，桌面构建）：

| | 可执行行 | 覆盖率 |
|---|---|---|
| 抽取前 | 116 | 95.69% |
| 抽取后 | **158** | **98.73%** |

**可执行行数涨了 36 行** —— 那正是从 `#ifdef` 里搬出来、现在真的会被
执行到的判据。唯一未覆盖的是 switch 里 `MISS_NONE` 的空 case
（两个调用点都在 `miss != NONE` 时才调，确实到不了）。

### 反向验证（逐条回退，全部实测变红）

| 回退的改动 | 变红 |
|---|---|
| `distanceDm / 10.0` → `/ 100.0` | 1 项 |
| 删掉闸门①（无距离） | **4 项**（含旧有 2 项） |
| 闸门③改成精确比 `(0,0)` | **4 项**（含旧有 2 项） |
| `OVER_MAX` 与 `GROUND` 合并 | 1 项 |
| 闸门顺序改成"零解先于无距离" | 1 项 |

先报"坐标非法"会把操作员引去查飞机定位，而实际该做的是瞄准。
