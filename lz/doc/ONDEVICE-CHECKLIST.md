### 0b. 在设备上

```bash
# 让出 PSDK 通道 —— 有进程就停掉（退出码 1 = 无进程 = 通道可用）
pgrep -x Smart3DExplore >/dev/null || /system/bin/dji_app_ctl stop Smart3DExplore

# 设备本机编译（绝不交叉编译）
# ⚠️ 三个 -D 一个都不能少 —— 漏了不会报错，只会**静默**产出错的东西：
#   LZ_BUILD_PSDK_APP 默认 OFF ⇒ 只编 lz_core 测试，**不生成 lz_app**
#   PSDK_ROOT 没有默认值 ⇒ 上面那个打开后不加它就 FATAL_ERROR
#   LZ_VISION_BACKEND 默认 stub ⇒ 「识别目标」永远报"已对准"（见 §0c）
# 构建目录必须是 lz/build-native（app.json 的 bin 相对 app_json 解析）
cd ~/lzbuild && cmake -S lz -B lz/build-native \
    -DLZ_BUILD_PSDK_APP=ON -DPSDK_ROOT=$HOME/lzbuild \
    -DLZ_VISION_BACKEND=hsv -DLZ_POLE_SOURCE_LASER=ON \
  && cmake --build lz/build-native -j4

# 判据：配置阶段必须出现这一行（没有 = 凭据没读进去）
#   已从 .../lz_credentials.ini 载入机载应用凭据（App ID 184842）

# 验证（设备 cmake 是 3.16，**没有** --test-dir 选项，必须 cd 进去）
cd lz/build-native && ctest --output-on-failure    # 判据：12/12 passed

# 打包安装（装包需要飞机通电并连接）
cd ~/lzbuild && tools/build_dpk/build_dpk.sh -i lz/app_json/app.json -o ~/dpk
dji_app_ctl install -i ~/dpk/liangzhourenwu_v01.00.00.00.dpk
```

传源码用 `--mtime="-60 seconds"`，**必须带 `--exclude='lz/build*'`**，
且不能用 `--mtime='@0'`（会让 make 静默跳过编译）。完整命令见 `lz/doc/BUILD-DEPLOY.md`
「设备侧打包清单」。

**装完先确认身份校验走完了**（`[V]` 2026-10-12 实测）：

日志在 **`/open_app/liangzhourenwu/data/logs/`**，按应用名分目录，不是
`/blackbox/...`。判据（文件名是 `DJI_NNNN_<日期>_<时间>.log`，`latest.log` 软链）：

```bash
L=/open_app/liangzhourenwu/data/logs/$(readlink /open_app/liangzhourenwu/data/logs/latest.log)
grep -c "dji_identity_verify.c:654" $L      # 判据：≥ 1
```

那个文件只有一行，内容是 `'data/logs/latest.log' -> 'DJI_0015_...log'`
（一个**字符串**，不是软链，且 `root:root` 写不了）。真正的日志在上面那个路径。

## 1. 控件对照表 —— ⚠️ **分两个界面，别在同一个地方找**

**8 个控件分布在两个界面**（归属由语义定，见 CLAUDE.md「Pilot 2 控件」一节）。
现场最常踩的坑是**在 PSDK 菜单里找不到半径/高度/航点数** —— 它们在
Payload Settings 里。

### 1a. `main_interface` —— Pilot 相机视图左侧「PSDK」菜单（**飞行中操作**）

| index | 类型 | 名称 | 出厂默认 | 映射 |
|---|---|---|---|---|
| 0 | switch | 绕飞 | OFF | OFF=STOP 急停；ON=上传航线并开始 |
| 1 | button | 记录飞机位 | — | 把飞机当前位置记为圆心 |
| 2 | button | 记录激光点 | — | 把激光瞄准点记为圆心 |
| 3 | button | 识别目标 | — | **视觉照准**：看画面 → 转云台，把目标对到画面中心 |
| 4 | button | 标定地面 | — | **起飞前**把激光打向地面，记下目标高的参考零点 |

### 1b. `config_interface` —— Pilot 的 Payload Settings「负载设置」（**起飞前配置**）

| index | 类型 | 名称 | 出厂默认 | 映射 |
|---|---|---|---|---|
| 5 | scale | 半径m | 50% | 0–100% → **5–20 m**（50% → 12.5 m） |
| 6 | scale | 高度m | 66% | 0–100% → **5–120 m**（66% → 约 80.9 m） |
| 7 | int_input_box | 航点数 | 8 | **直接填个数**，夹到 3–64 |

⚠️ **索引 0–7 是**一个连续序列、跨界面不重复** —— SDK 的 handler 表是扁平的。
改任何控件的界面归属时，索引必须跟着重排，且两份 json 同步。

⚠️ **`int_input_box` 只能放 `config_interface`** —— 放进 `main_interface` 时
SDK 收下它但不渲染成可编辑控件（表现：看得见、改不了、回调零命中）。

⚠️ **「标定地面」必须在 `main_interface`（2026-10-13 新增）** —— 标定要把激光
打向地面，而**瞄准要看相机画面**，相机视图里只有 PSDK 菜单。放进
Payload Settings 的话操作员得在两个界面之间来回切，看不见画面就没法瞄。
**这正是它不能和半径/高度放一起的原因。**

⚠️ **控件 3（识别目标）与控件 0（绕飞）互斥，且两个方向都拦**（判据 `LzAlign_CheckConflict()`，
`tests/lz_test_align.c` 有用例）。绕飞在跑时按控件 3 会回一条提示；照准在跑时
拨控件 0 **不清开关**，只在照准结束后自动启动（理由：操作员多半就是
"先识别、再绕飞"，清掉开关会逼他再拨一次）。

**控件不在妙算3 应用管理面板里**（那里那个按钮只是 `dji_app_ctl start`）。

## 2. 航线参数（用于对照观察，不要照抄去改代码）

| 项 | 当前值 | 出处 |
|---|---|---|
| 航点转弯模式 | `toPointAndPassWithContinuityCurvature` + `useStraightLine=1` | `lz_mission.c` 的 `LZ_TURN_PASS_WITH_CURVE` |
| 提前转弯截距 | 最短段的 45%（8 点 20 m 半径 → **6.888 m**） | `LzPlan_SuggestDampingM()` |
| 机头朝向 | `towardPOI`，兴趣点 = 记录的杆位 | `lz_wpml.c` |
| 云台俯仰 | **几何反算**（见下） | `LzPlan_ComputeGimbalPitchDeg()`，`lz_mission.c` 的 `autoGimbalPitch=true` |
| 巡航速度 | 3.0 m/s | 同上 |
| 收尾动作 | `gotoFirstWaypoint` | `lz_wpml.h` 的 `LZ_WPML_FINISH_ACTION` |
| 返航高度 | `max(航线高度, 30)` | `lz_wpml.c`（手动/失控返航时生效） |
| 机型/负载枚举 | `droneEnumValue=99` / `payloadEnumValue=89` | `LzWpml_DefaultIdentity()` |
| 航点总数 | `waypointCount + 1`（末尾补了与首点**坐标完全相同**的收尾点） | `lz_plan.c` |

**云台俯仰现在是算出来的，不再是写死的 −15°**（2026-09-25 改）：

    俯仰 = -atan2(飞机相对目标高度 - 目标高, 半径)

⚠️ **2026-10-12 起瞄的是「杆顶」而不是「杆中点」**（早先是 `- 目标高/2`）。
理由是现场要的是**红旗落在画面中心**，而旗挂在杆顶。
代价已确认接受：**低高度 + 大半径时杆的中下段会落到画面下缘之外**。

⚠️ **2026-10-13：目标高改由「地面标定基准」算，必须先按「标定地面」**。
原先是「激光海拔 − 起飞点海拔」，而实测证明两者**参考面不同**
（椭球高 vs 气压高），系统性偏约 38 m —— 现场瞄地面算出 38.25 m、
瞄杆顶算出 53.75 m（真实杆高约 16 m），俯仰**方向都反了**（差 102°）。
完整证据链见 [`LASER-AND-POLE.md`](LASER-AND-POLE.md)。

⇒ **每次换场地、重新上电后，起飞前第一件事是按「标定地面」**：
飞机停在起降点，把激光打向附近平整地面，按按钮。浮窗回
`✓ 地面基准已标定：XX.X m` 才算成。**没标定时俯仰会瞄地面那一层**，
而画面上看不出异常 —— 启动时浮窗会提示「地面基准**未标定**」。

**可控范围 −90°~70°**（2026-09-26 更正，见 `lz_plan.h` 的常量。
早期记录的 +30° 是错的 —— 那是照抄 M4E；DJI 官网 M4T 是 70°，
固件说明里也有「M4T gimbal now supports up to 70° upward tilt」）。

现场对照表（**本场地实测杆高约 16 m**，2026-10-13 用新公式反算：

    杆顶激光海拔 49.6 − 地面基准 33.5 = 16.1 m

⚠️ 下表按 **15 m** 算 —— 与实测的 16 m 差 1 m，低空（20–40 m）下俯仰差
约 2–3°，够用；**要更准就把表里的杆高换成实测值重算**）：

| 半径 | 高度（相对起飞点） | 俯仰 | 可达 |
|---|---|---|---|
| 5 m | 80 m | −85.6° | ✅ |
| 12.5 m | 80 m | −79.1° | ✅ |
| 20 m | 80 m | −72.9° | ✅ |
| 20 m | 20 m | −14.0° | ✅ |
| 12.5 m | 比杆**低** 10 m | +63.4° | ✅（上仰） |
| 12.5 m | 比杆**低** 30 m | +74.5° | ❌ 超 70° |
| 5 m | 比杆**低** 20 m | +81.9° | ❌ 超 70° |

⚠️ **最后三行是要现场记住的**：飞机比杆低的时候需要**上仰**，
而上仰能力只有 70° —— **飞机低得越多、半径越小，越可能够不着**。
够不着时 `LzPlan_Validate` 会在起飞前用 `LZ_ERR_RANGE` 拒掉
（这是刻意的：把"物理上做不到"变成起飞前的明确错误，而不是上机后
相机纹丝不动却不知道原因）。

⚠️ **改瞄杆顶后上仰更容易越界**：同样是"低 10 m / 半径 12.5 m"，
瞄中点时是 +54.5°，瞄顶端变成 **+63.4°** —— 余量从 15.5° 缩到 6.6°。
**飞机比杆低时请留更多余量。**

⚠️ **判据**：绕飞时机头对杆（`towardPOI`），**杆顶（旗）应大致停在画面中央**。
若杆明显偏在画面上缘或下缘，说明俯仰算错了（或目标高填错了）——
先量实际杆高，再看 `LzPlan_ComputeGimbalPitchDeg` 的输入。

⚠️ 原 −15° 只在"低高度 + 大半径"下碰巧接近；默认滑杆值（半径 12.5 m、
高度 80.9 m）下正解是 **−80.3°**，差 65° —— 而画面上看不出"没对准"，
只会觉得"杆在边上"。

**8 点 20 m 半径的几何**（对照 Pilot 显示的里程）：
单段弦长 **15.307 m**、总路径 **122.459 m**、整圈周长 125.664 m。
Pilot 显示里程若接近 125.7 说明它按周长算（错），接近 122.5 才对。

### 3.0 ⚠️ 标定地面基准 —— **本场次第一件事，不做则俯仰全错** `[ ]`

**2026-10-13 新增的步骤**。目标高现在由「激光海拔 − 地面基准」算，而基准要标。

- [ ] 在 PSDK 菜单里按 **「标定地面」**（index 4），把激光打向地面。
- [ ] 浮窗应回 `✓ 地面基准已标定：XX.X m`。**记下这个数** ——
      它应当**接近飞机所在位置的地面海拔**（本场地实测约 33.5 m）。
- [ ] 之后按「记录激光点」瞄准**杆顶**，浮窗应回

`地面基准未标定 —— 起飞前请按「标定地面」按钮`。此时记杆顶得到的目标高是 0

⚠️ **别在起飞后标**：那时"地面"标成了"飞机下方那层"，之后所有目标高整体偏掉。
浮窗会报出基准值，就是让你能发现这种情形。

## 3.13 云台偏航撞限位 / 云台电机异常 ⚠️ **已修，待复验** —— 2026-10-01

### 现场现象（用户 2026-10-01）

> 无人机在绕飞的时候云台显示**偏航角达到限位**，然后显示**云台电机异常**，
> **结束绕飞航线后又正常了**。

### 根因（三现象全部对上）

`FREE` 的语义是「在地面坐标系里固定云台姿态，**忽略飞行器运动**」
（`dji_typedef.h` 的 `DJI_GIMBAL_MODE_FREE` 原文）。而 M4T 的 pan 轴是
**相对机头**的机械软限位 ±60°。于是「保持地面姿态」只能靠 pan 关节
**反向补偿**机身转动：

```text
绕飞（towardPOI）⇒ 机头绕杆连续转 360°
FREE 要求云台保持地面姿态 ⇒ pan 关节必须反向走 −360°
pan 只有 ±60°  ⇒ 绕出去 60° 就顶到机械限位，然后一直顶着
```

顶住之后电机还在往限位方向给力 ⇒ 报**云台电机异常**。航线一结束、
遥控器拿回云台控制权并恢复跟随，关节松回来 ⇒ **「结束后又正常了」**。

### 为什么会有 FREE 残留

`FREE` 是 2026-09-29 为**横向照准**加的（`YAW_FOLLOW` 下云台 yaw 跟随机身，
会和我们下发的绝对方位角抢）。照准本身是**静止观测**，`FREE` 在那里是对的
—— 错在**用完不还**，而绕飞恰好是「机头连续转 360°」的场景，正是 `FREE`
唯一会出事的场景。

### 三处修复

| 位置 | 修什么 |
|---|---|
| `lz_visual_align.c` 的 `teardown()` | 收尾把模式**恢复成 `YAW_FOLLOW`**（借了要还） |
| `lz_visual_align.c` 的 `do_finish_done/fail()` | 宣布"完成/失败"**之前**先 `teardown()` —— 消掉"已宣布完成但模式还没还"的窗口 |
| `lz_mission.c` 的 `lz_mission_start_orbit()` 开头 | **防御性**再设一次 `YAW_FOLLOW` —— 进程被杀、或飞机上残留着旧版本留下的 `FREE` 时兜底 |

### 新增的可观测性（此前这两件事**日志里一个字都没有**）

> 🚨 **2026-10-12 实测：这条订阅在 M4T 上订不上**（`rc=0x00000100` NOT_FOUND，
> 飞机固件没挂这个话题）。**本节以下全部内容在修复前都不会产生任何输出** ——
> 包括本节末尾「上机复验」的四条判据。详见 **§0c**。

订阅了 `TOPIC_GIMBAL_STATUS`（10Hz，**不是**被照准订走的 `GIMBAL_ANGLES`），
主循环里**只在内容变化时**报一行：

```text
云台状态：偏航限位 偏航电机异常
```

⚠️ 输出是「**只列报警项**」的短词形式，不是定长表格 —— 表格里 `偏航`
会在限位段与电机段各出现一次，两件事会撞在一起，而它们的处置完全不同。

⚠️ **极性是从头文件抄的**（限位 `1`=顶限位 / ESC `1`=**正常**，两者相反）。
抄反了不会报错、桌面测试也测不出来，只会让告警**恰好反过来**。
⇒ 收到**第一帧**时打一次**原始位图**，拿它核对：

```text
云台状态原始位图（首帧，仅一次）：0x00000000  限位[pitch=0 roll=0 yaw=0]  ESC[...]  ...
```

**标定方法**：把云台顶到某个轴的限位，看这一行里**哪一位翻转**，
与 `src/lz_bridge_psdk.c` 里那张 bit 表对一遍（bit2/3/4 = 三轴限位、
bit11/12/13 = 三轴 ESC、bit10 = gyroFalut、bit0 = mountStatus）。

⚠️ 格式化逻辑已抽到 `lz_core` 的 `src/lz_gimbal_status.c`（零依赖、桌面可测），
判据的反向验证在 `tests/lz_test_gimbal.c` 末尾。

### ⚠️ 这一轮踩的四个坑（每一个都花了几小时）

#### 坑 1：**Pilot 会攥着缓存的控件会话不刷新**（最耗时的那个）

**现象**：控件突然全部无响应，**重启应用无效**。

**判据**（决定性，一看就分清）：

| 现象 | 含义 |
|---|---|
| 日志里 `0x3C1A` 有、`set widget value` 有 | 正常 |
| 心跳 `0x2105` 一直在，但 `0x3C1A` 为 0 | **Pilot 没把按键发出来** |
| 卸载应用后 Pilot 的「PSDK」菜单里**那一栏还在** | Pilot 显示的是**缓存**，不是设备实况 |

**证据**（同一份二进制，时好时坏）：

```text
14:39  0x3C1A=652  按键=2   ← 能用
14:42  0x3C1A=0    按键=0
15:05  0x3C1A=0    按键=0   ← 用户点了没反应
（卸载应用 → 用户说 Pilot 里仍能看到「视觉航点规划」← 缓存实证）
（重新装回 → 用户刷新界面后 0x3C1A 立刻恢复）
```

**恢复办法**：让 Pilot 重建控件会话 —— 刷新/重进「PSDK」菜单、
或在 Pilot 侧动一下（本次是重装应用 + 用户刷新界面后恢复）。

⚠️ **不要再往"我的代码有问题"方向排查**：先查 `0x3C1A`。
它到了才是应用侧的问题；它没到就与代码无关。

#### 坑 2：**启动期重复按压 = 照准自杀**

按下 → `do_init()` 里两个阻塞 SDK 调用合计约 **1.6 秒**
（实测 01:51:47.359 按下 → 01:51:49.004 开流）→ 操作员以为没反应又按一次
→ 那一拍被判成"再按一次 = 停止" ⇒ **照准启动后 100 ms 自杀**。

**已修**：`LzAlign_DecideToggle(canStop, inGrace)` 三选一（开始/停止/**吞掉**）
+ 2 秒启动保护期 + **按下当场回执**（打断"没反应→再按一次"的循环）。

#### 坑 3：**`DjiLiveview_Deinit()` 会吃掉 Pilot 的飞行画面**

`LzVisionSource_Stop()` 原先调它，而它反初始化的是**整个 liveview 模块** ——
妙算3 转发给 Pilot 的图传正走这个模块 ⇒ 跑一次照准黑一次画面，且不自恢复
（`systemctl restart dji_sdk_agent` 需要 root，dji 用户做不了）。

**样例为什么那样写没问题**：官方 `test_liveview.c` 是一次性工具，Deinit 与
进程退出相隔几毫秒，用户看不到。**我们是常驻应用。**

**已修**：只 `StopImageStream`，不 Deinit。

⚠️ **本次的黑屏最终归因到云台自检失败**（Pilot 报「自检失败，请检查云台三轴电机
无卡」），**不是**这一条造成的 —— 时间上 Deinit 发生在 01:51，而故障早于此。
**但这条修改本身仍然正确**（常驻应用不该关掉别人的画面）。

#### 坑 4：**构建目录必须是 `lz/build-native`**

`app.json` 在 `lz/app_json/`，其 `bin` 字段是 `../build-native/bin/lz_app`，
`build_dpk.sh` **按 json 所在目录解析** ⇒ 必须是 `lz/build-native/`，
**不是仓库根的 `build-native/`**。在仓库根建会报
`Error, bin field ../build-native/bin/lz_app not exist`。

## 5. 遇到问题时的排查顺序

1. **通道被占** → `pgrep -x Smart3DExplore` 有进程就
   `/system/bin/dji_app_ctl stop Smart3DExplore`。
   症状是误导性的"机型不匹配"报错，不是通道报错。
2. **启动被拒** → 看日志里的前置条件四行（飞行状态 / RC 档位 / GPS / 起飞点）
   + `error_code` 原始值（`%llX`）。
3. **进程闪退** → 优先怀疑「控件回调里做了阻塞调用」。
   症状：日志戛然而止于 `dji_msgq.c:227 semaphore wait timeout` +
   `dji_linker.c:309 send msg to queue error`。
4. **改完代码行为没变** → 回看是不是 `tar --mtime` 把时间戳弄反了，
   导致 `make` 静默跳过编译（传了新代码、跑的还是旧二进制）。
