航线闭环

闭环不是「有反馈就算闭环」。对这条航线来说，该闭的只有一层 —— 位置可以开环，云台必须闭环。而这条分界线，是平台能力划出来的，不是算法选的。

01

一个回路，六个环节

点任意一个环节看它的状态。绿色 = 已接通，橙色 = 代码在但未生效，红色 = 断。

这个回路在问什么

回路的核心是相位 —— 风轮停在（或转到）哪个角度。它既是规划器的输入， 又是视觉要测的量。闭环的全部意义，就是让这两头接上。

顺时针走一圈：相位 → 规划 → KMZ → 执行 → 拍照 → 视觉反解 → 回到相位。 另有一条支线：相位 → 云台，在执行途中实时调整指向。

02

什么时候才需要闭环

判据只有一条：相位是常量，还是观测量？

作业模式
相位是台账常量，一次规划即可
停机受控风轮可转动
相位从哪来 台账常量（现场实测填 park_phase） 实时观测量（视觉反解）
规划 开环，一次生成 仍需一次假设相位
安全靠什么保证 离叶片轴线的距离 离盘面的轴向距离（与相位无关）
闭环必要性 不必要 必须

停机时，回路本来就是断的 —— 而且这样没问题

停机受控作业下，相位在起飞前就测好了、写进台账，飞行中不会再变。 这时候「视觉反解 → 相位」那一段不需要存在：规划器拿到的相位是对的， 一次生成航线即可。

只有风轮可能转动时，相位才变成必须在飞行中持续测量的量 —— 回路才必须真的闭上。

03

该闭在哪一层

这是整页最要紧的一节。结论是：位置层开环，云台层闭环。 拖动滑块 —— 叶片在动，站位不动，云台跟着转。

站位（开环，固定） 叶片（转动） 风轮盘面 云台视线（闭环，跟随）
20°
01

位置为什么能开环。转动模式下的安全判据用的是 离盘面的轴向距离（|along| < min_safe_dist）， 而不是叶片位置 —— 这个量与相位无关。更关键的是，规划器会把站位 自动推到盘外至少 min_safe_dist 处。所以无论相位假设对不对，站位都是安全的。

02

位置为什么只能开环。执行单元是 KMZ 预下发的航点文件。 任务一旦启动，航点就固化了 —— 飞行途中改不了位置。 想改只能重新生成 + 重新上传，那是分钟级的，跟不上风轮转动。

03

云台为什么能闭环。云台是唯一在飞行中可实时干预的执行器 —— DjiGimbalManager_Rotate 是直接调用，不依赖 KMZ 动作表。 所以「对准叶片」这件事，只能交给云台。

于是闭环被拆成两条，快慢分明

慢回路（规划级）：相位 → 重规划 → 重新上传 KMZ。分钟级，跟不上转动。
快回路（执行级）：相位 → 云台指向。毫秒级，飞行中唯一有效的闭环。

代价要说清楚：位置开环意味着站位是按某个假设相位摆的。相位错了， 站位仍然安全，但可能不在叶片附近 —— 拍出来的 GSD 与预期不符。 云台闭环能补指向，补不了站位。

04

现状：断在哪

快回路的代码已经写好了，但它的感知端是空的。断点不在算法，在没有图进来。

/* 快回路：代码完整，但进不来 */ if (cfg->profile.rotorMayRotate && runner->telemetry.rotor.valid && target->bladeIndex >= 0) { predicted = WtTelemetry_PredictRotorFrame(&telemetry, 0.3); /* 外推 0.3s */ tip = WtTurbine_BladeTip(&predicted, spec, target->bladeIndex); wantYaw = WtEnu_Azimuth(...); /* 指向叶尖 */ } /* 但 rotor.valid 唯一的置位入口是 —— */ WtTelemetry_UpdatePhaseEstimate(...) ← 只被 SolvePhaseFromVision 调用 WtTelemetry_SolvePhaseFromVision(...) ← 全仓库无人调用
环节状态说明
规划 → KMZ → 执行已接通 KMZ 上传、任务启动、监控循环完整
遥测订阅已接通 位姿、云台姿态、RTK 状态、电池
云台跟踪（快回路）代码在，未生效 默认 gimbal_track_gain = 0 关闭；且只在航点序号变化时触发一次，不是连续跟踪
相位视觉反解代码在，无人调用 SolvePhaseFromVision 接口与实现都完整，但没有调用者
取图不存在 只有 StartShootPhoto 触发快门，没有 liveview 订阅，也没有照片回传

断点是一条链，不是一处

取图不存在 → 照片进不了视觉模块 → SolvePhaseFromVision 没有输入 → rotor.valid 永远是 false → 云台跟踪那个 if 永远不成立 → 快回路整条空转。

所以「闭环没生效」的根因不在闭环代码本身（它写得很完整，含 0.3 s 外推、 死区、低通滤波、转速估计），而在更上游的取图能力。 这也解释了为什么把 gimbal_track_gain 调大也没用 —— 感知端是空的。

05

补齐的顺序

断点在感知端，所以补的顺序是从下游往上游倒着来会白做 —— 必须先把图取到。

01

先取图。接入 liveview 订阅（实时、低延迟，适合跟踪）或照片回传 （分辨率高，适合精测）。这一步不解决，后面全都无从验证。

02

再接通视觉。把图像里的叶尖方向按相机内参换算成相对光轴的偏角， 喂给 SolvePhaseFromVision —— 它的入参就是这两个角，接口已经为这一步留好了。

03

然后才开云台跟踪。把 gimbal_track_gain 从 0 调开。 此时 rotor.valid 才会真的为真，快回路才第一次真的闭上。

04

最后才是调参。死区、低通系数、外推时长（当前写死 0.3 s）都要按实测响应调。 这些参数现在都是拍脑袋的默认值 —— 因为回路从没真跑过。

还有一处架构上的待办

云台跟踪目前挂在航点到达事件上（HandleWaypointActions）， 而不是挂在主循环的每个周期上。所以它是离散触发的 —— 航点之间飞行时云台不动。

真正的「实时跟踪」应该把它移到 10 Hz 的主循环里，按固定周期算指向。 这件事独立于取图，可以先做，但做了也看不出来效果（因为相位还是无效的）—— 所以顺序上仍排在取图之后。

依据：wt_runner_psdk.c（执行与云台）、wt_telemetry.c（相位估计）、 wt_plan.c（安全判据与站位）、wt_app_config.c（默认参数）。

状态判定以当前分支代码为准；「代码在，未生效」指实现完整但无调用者或默认关闭。
